# Repository Guidelines

## Project Overview

Kindle Recipes is a deliberately small recipe library for Kindle browsers and ordinary desktop browsers. It is a single Rust/Axum process: Askama renders every page server-side, SQLite holds all data, and a Node worker built on the Pi SDK generates recipe drafts through a ChatGPT (Codex) or Claude subscription or a provider's API key.

Access control is per account with a native sign-in page: the first visit redirects to `/setup` to create the first username and password (stored as an Argon2 hash in SQLite), and setup signs the browser in. Every library route then requires a session: a signed-out visitor goes to `/login`, and a successful sign-in sets an `HttpOnly` session cookie. Each account has its own library, drafts, settings, and AI logins (subscriptions and API keys). Accounts form **groups** (a household; `src/groups.rs`): an account is in at most one group, which the first accepted email invite creates with the inviter and the invitee; any member invites more, any member leaves, and the last but one to leave dissolves it (no admin role or removing others yet). Members share chosen recipes read-only with each other (`recipes.shared`, the library's Group view, Save a copy), and each member chooses which other members may generate with its AI logins (`ai_grants`), used only while the grantee has no AI setup of its own. The account avatar at the right of the header opens the account menu (`<details>` in `base.html`): it lists only the other accounts this browser is signed in to (never the server's other users), switches to one at once, and offers **Sign in to another account** (`/login`), **Create account** (`/accounts/new`, any signed-in user may add one), **Sign out** of the active account, and **Sign out of all accounts**. A browser stays signed in to up to 8 accounts. The signed-in user can change their password at `/settings/password` (current password required). The change ends every session of the user, so other devices must sign in again; the browser that made the change gets a new session. The signed-in user can also delete their own account at `/settings/delete-account` (linked from the Account block in Settings): a confirmation page with no password, which says everything the account owns is deleted for good, and a `data-confirm` form. Deleting removes the account and all its data, ends its sessions everywhere, and hands this browser to its next signed-in account. Sign-up is never open to signed-out visitors except through a live group invite link (`/invites/{token}`, the invite is the ticket), but any account holder can create accounts (at most 10 an hour per client address). Brute force is limited in memory (`auth::RateLimits`): failed sign-ins per client address and per username, wrong current passwords per user, and accounts created per address; a limited request gets its form back with 429 and "Try again in N minutes." `/setup` is open to anyone until the first account exists, so finish setup before exposing the server.

## Architecture & Data Flow

Single-process Axum 0.8 app (crate `kindle-recipes`, edition 2024, binary-only — no `lib.rs`):

- `src/main.rs` — the hub: `#[tokio::main]` bootstrap (migrations, `ai::remove_leftover_temp_files`, legacy credential import, `retire_codex_models`, `reconcile_ai_provider`, `fail_interrupted_chats`, then it spawns the hourly `prune_expired_drafts` and, with an embedder, `search::backfill`), env config, `routes()` router, `AppState`, `AppError`, shared serde types, Askama template structs, form/validation helpers, the Settings handlers (`settings_page`, which renders `settings_view`, also used by `groups::send_invite`, `update_settings`, `add_endpoint`, `add_web_search_key`, …) with `PROVIDER_PRESETS`, the Codex device-code and Claude copy-code sign-in handlers, `run_node_script` (sign-in helpers through `ai::run_node`, killed after `AUTH_SCRIPT_TIMEOUT`, 60 s), and `image_response` / `not_modified`: every locally produced JPEG (dish photos, candidates, draft thumbnails, stills, note photos) is served `Cache-Control: private, no-cache` with an ETag from the bytes' SHA-256, and the `not_modified` layer on every route answers a matching `If-None-Match` with 304. The settings accessors live in `src/settings.rs` and are re-exported here (`pub(crate) use settings::*`), so callers name them from the crate root (`crate::app_setting`, `crate::ai_account`, …).
- `src/auth.rs` — user accounts and cookie sessions: `auth_middleware` (protects every route in the `protected` router and scopes the `ACCOUNT_MENU` task-local that `base.html` reads through `account_menu()`), `AuthUser` extractor, multi-account handlers (`new_account_page` / `create_account`, `switch_account`, `logout_all`), `hash_password` / `verify_password` (Argon2), `setup_page` / `setup_create`, `login_page` / `login`, `logout`, the brute-force limits (`RateLimits`, `Limit`, the `ClientAddress` extractor, `username_key`, `address_bucket`, `try_again`), `reset_password_page` / `reset_password`, `delete_account_page` / `delete_account` (account deletion; `delete_user` holds the one-transaction delete, and takes the account out of its group first with `groups::leave_group_in`), plus two helpers for `groups.rs`: `signed_in_user` (the browser's active account, for the invite page outside the middleware) and `sign_in_browser` (signs a browser in after sign-up through an invite).
- `src/settings.rs` — what each account keeps besides its recipes, and the only queries on those tables outside account setup and deletion in `auth.rs`: `app_settings` (`app_setting` / `set_app_setting` and the typed readers `ai_provider`, `selected_model`, `selected_claude_model`, `selected_effort`, `media_cleaner_setting`, `measurement_system`, `step_moments_enabled`, `keyword_search_selected`, …), AI resolution and grants (`provider_configured`, `own_ai_configured`, `ai_account`, `ai_grants_received`, `ai_grantees`, `set_ai_grants`, `AI_SOURCE_SETTING`), subscription credentials (`pi_credential`, `store_pi_credential`, which clears `auth_failed_at`, `store_refreshed_pi_credential`, `remove_pi_credential`, `mark_login_refused`), AI endpoints (`list_endpoints`, `find_endpoint`, `insert_endpoint`, `remove_endpoint`), the web search key, and the startup healers `reconcile_ai_provider` / `retire_codex_models`.
- `src/ai.rs` — the AI pipeline: the Add recipe card (`add_recipe_page`, `generate_recipe`, `route_prompt`, `start_import`; `generate_page` sends `GET /ai/generate` and `/ai/import` to the card) and the draft handlers (`draft_page`, `alter_draft`, `apply_draft`, `cancel_draft`); `pi_recipe` (generation), `chat_reply` (recipe chat), and `clean_media_evidence` (video cleaner), which each resolve a backend (`resolve_backend` → `RecipeBackend::{Subscription, Endpoint}`) and run through `run_with_retry`; the worker runners (`run_node`, `run_worker`, `run_subscription_worker` with its `TempAuthFile`); `track_login` and the login checks; the model catalogue (`discover_models`); the recipe system prompts, built with `concat!` from the `recipe_contract!`, `exclusion_rule!`, and `evidence_prompt!` macros, so a shared rule changes in every prompt: `RECIPE_PROMPT`, `GROUNDED_RECIPE_PROMPT` (with its own, researched exclusion rule), `EVIDENCE_RECIPE_PROMPT`, and `EVIDENCE_OFFLINE_RECIPE_PROMPT` (both with the exclusion rule), picked by `system_recipe_prompt(evidence, search_mode)`, and `retry_guidance` takes the same pair; `recipe_schema` / `validate_generated` / `normalize_generated` / `dedupe_sources`; the video import and media-debugger runs (`AppState.media_debug_runs`, each owned by the account that started it: the debugger lists only that account's runs, another account gets 404, and `forget_media_runs` drops a deleted account's runs); and `remove_leftover_temp_files` (startup: `kindle-recipes-auth-*.json`, `kindle-recipes-media-*`, and `kindle-recipes-upload-*` in the temp directory). The Add card prompt and the draft alteration box take at most 4000 characters, carriage returns not counted (`MAX_PROMPT_CHARS`).
- `src/chat.rs` — recipe chat (the **Ask** drawer on the recipe card, which replaced "Alter with AI" and is the only way to change a saved recipe with AI; the old `GET /recipes/{id}/ai/alter` URL is `alter_redirect`, which opens the drawer): `panel` builds the drawer for `recipe_page`, `ask` stores a question with a `pending` answer (`start_chat_turn` checks for a running answer in the same INSERT; a busy thread flashes `chat_busy`) and runs it on a spawned task (`chat_library` + `library_summary` + `chat_prompt` → `ai::chat_reply` → the worker's `chat` command, whose tools read the recipe's notes, their photos, and saved versions, and search the web (see Web search below); the system prompt also covers a cook coming back after cooking for pointers next time), `keep_answer` (Keep as note: an answer becomes a whole-recipe note linked by `recipe_notes.chat_message_id`), `toggle_drawer` (open state is the user's `app_settings.recipe_chat_drawer`, so it stays open across edits, views, and recipes), `clear`. When the cook asks for a change, the model edits a copy of the recipe with the worker's edit tools (`pi/recipe-edits.ts`: `change_details`, `add/change/remove/move_ingredient`, `add/change/remove/move_step`, numbered from 1 in the current order; each item keeps `from`, its index in the recipe sent, or null when new) and the reply carries the result as `proposal`. `answer` stores it, if `valid_proposal` passes, as `recipe_chat_messages.proposal_json` (`ChatProposal` `{before, after}`) with `proposal_base` (the recipe's `updated_at`) and `change_state='ready'` (`finish_chat_answer` with `AnswerProposal::{None, Refused, Ready}`); a proposal that fails it is stored as `change_state='failed'`, and the drawer says the change was not made. The drawer lists only what differs (`proposal_view`: details before → after, ingredients and steps added / removed / changed / moved, changed text marked word by word by `word_diff` in `<ins>`/`<del>` with + / − markers for e-ink) under **Accept** (`POST /recipes/{id}/chat/{message_id}/accept`, `accept_change`) and **Deny** (`…/deny`, `decline_change`). Accepting runs `recipes::accept_chat_proposal` in one transaction: refuses (`change_stale`) once `updated_at` moved; keeps the block rows of kept items (so their step moments survive), deletes removed ones, inserts new ones, replaces step ingredient lines, drops `chart_json` only when ingredients or steps changed, clears the plate name when the title changed, writes the `change` divider (`divider_label`: the model's `label` tidied by `model_label` to at most 3 words, else `change_summary`), and records version `Chat: <label>`; then `moments::spawn_recipe_refresh`. `return_target` keeps the drawer's `back` on the same recipe page with its query (`?serves=N` on the card, `?view=chart&step=N&serves=N` in the chart).
- `src/notes.rs` — the cook's notes: text, a photo, or both, on the recipe as a whole or pointed at one saved version (`recipe_notes.version`, a number rather than a key, so a note still names a deleted version). `panel` builds the block for the recipe page (every note) and each version page (that version's notes; new notes there are about it) from the versions list the page already read; `add_note` (multipart, `hx-boost="false"`, photo normalised by `recipes::normalize_upload_jpeg` with `NOTE_PHOTO_FILTER`, at most 1280 px; only ffmpeg's output is stored, so an upload ffmpeg cannot convert is refused), `update_note` (text and "About"), `delete_note`, `note_photo` (owner only). "About" is `""` (whole recipe), `current` (the newest version, which matches the recipe now; a recipe with no history gets its "Original recipe" version first, `recipes::current_version`), or a version number that must exist; the Edit form of a note already about the newest version sends that version's number instead of `current`, so a version made meanwhile does not move it. `return_target` keeps `back` on the recipe page (any query, through `chat::return_target`) or one of its version pages.
- `src/recipes.rs` — recipe CRUD handlers **and the SQL accessors** for recipes, blocks, versions, drafts, thumbnails, moment pools, the search index, chat threads, and notes (`find_recipe`, `blocks`, `step_ingredients_by_step`, `sources`, `find_draft`, `recipe_snapshot`, `insert_blocks`, …); `begin_write` opens every multi-step write (`BEGIN IMMEDIATE`). `find_recipe` takes any executor (`&s.db`, `&mut *tx`, `&mut *conn`) and selects named columns plus `has_photo` and `shared`, so a new `Recipe` field must be added to its SELECT and to `find_readable_recipe`'s. `find_readable_recipe` returns the viewer's own recipe, or another member's shared one with its `SharedOwner` (see Shared recipes under Key invariants); `set_recipe_shared`, `group_cards`, and `copy_recipe` sit beside it. `insert_blocks(tx, recipe_id, ingredients, steps)` is the shared block insert (`apply_draft`, `restore_version`, and the new rows of `accept_chat_proposal`). `RecipeSnapshot` records `plateName`, so a plate-name edit is its own restorable version (a version stored without the field keeps the plate name on restore under the same title and clears it under another). The newest version cannot be deleted (`delete_version` answers 400, and the version page hides Delete), so it always matches the live recipe, which `current_version`, the notes' `current`, and the chat's `currentVersion` rely on. The step edit form shows only saved ingredient links (inferred ones show as pills and in the chart); saving an unchanged block records nothing and keeps the chart. `keep_recipe_view` (a layer on the protected router) puts the page's checked `view=chart`, `step`, and `serves` (1–48) back on a POST answered with a redirect to the bare `/recipes/{id}` of the page it came from, read from `HX-Current-URL`, else `Referer`. `JobSlot` releases a `thumbnail_jobs` / `moment_jobs` entry on any exit; `a_to_z_key(title)` is the shared A–Z order; `delete_recipe` deletes the recipe's `recipe_thumbnail_candidates` in the same transaction.
- `src/scale.rs` — servings scaling for the recipe page (pure, no I/O): `Scale::new(recipe.servings, ?serves=)` picks the factor, `scale_text` scales the amount at the start of a quantity or step ingredient line ("1 1/2", "1-1/2", "1⁄2", "½", "200g", "2–3"; every common vulgar fraction glyph, any whitespace including NBSP between a whole number and its fraction, and a second measure after a slash, "400g/14oz") and rounds metric g/ml/kg/l to round figures (fives from 100, whole numbers from 10, one or two decimals below) and everything else to kitchen fractions (halves, thirds, quarters, ⅛); text with no amount it can read whole ("to taste", "1,5 kg", a "3-2" dash) stays as written. The recipe page offers 1–6 (plus the recipe's own count) as plain `?serves=N` links that swap `.paper`; `scale.query` (`&serves=N`) rides on the chart and view links and `scale.page_query()` (`?serves=N` or empty) on the card's own links, and the moments poller, the Edit link, the details Cancel, and the block edit links carry the servings too. `RecipeQuery` reads `?serves=` and `?step=` leniently: a bad or empty value shows the page as written instead of a 400. Only the shown text scales: edit forms, the stored recipe, and the chart's validation keep the amounts as written. Units are the user's `app_settings.measurement_system` (`metric`, `imperial`, `source`/absent; `POST /settings/measurements`, block `settings-units`): `measurement_rule` adds a line to the generation field rules (`pi_recipe`, read from the requesting user, not the AI account) and to the chat system prompt.
- `src/chart.rs` — pure cooking-flow chart builder (`build_chart`, `selected_chart_step`), no I/O.
- `src/thumbs.rs` — local dish-thumbnail pipeline for video imports: ffmpeg frame sampling, pixel scoring, diversity selection, square cropping, and (with the embedding sidecar) `order_by_dish_margin` ranking of a 12-crop pool against dish/non-dish prompts. Pure functions are unit-tested; one integration test needs ffmpeg (present in the Docker builder stage).
- `src/media.rs` — social video import: URL validation, one yt-dlp call for metadata and video (metadata-only fallback), then two lanes on scoped threads — audio ffmpeg → `transcribe_audio`, frames ffmpeg → `read_video_text` — and the OCR planner (`plan_ocr_jobs`: a 1 Hz grid of the 4 Hz candidates plus shot-change onsets; the grid and the cut window follow the cadence the frames were actually extracted at, so a video below the scan rate still gets a 1 Hz grid, and when onsets alone exceed `OCR_MAX_FRAME_JOBS` (160) exactly that many are kept, spread evenly) and OCR cleaner (`frame_capture` → caption chains → one snippet per card, rows joined with ` / `). `cleaner_prompt` / `recipe_prompt` build the prompts (the cleaner prompt treats audio and OCR claims the caption does not support as uncertain; the recipe prompt mentions web search only for a model that has it). One blocking job per extraction owns the media permit and a `Workdir` guard; it delivers the evidence as soon as both lanes finish, then runs thumbnails and the moment pool, which `PendingExtras::finish()` collects. Both re-download paths (dish-photo re-pick, `extract_fresh_thumbnail_candidates`, and moment re-capture, `extract_fresh_moment_pool`) share `with_fresh_download`, built on `run_staged_job`, which logs every warning. `run_ffmpeg` is the one ffmpeg entry point (`MEDIA_FFMPEG_PATH`, plus `-nostdin -y -hide_banner -loglevel error`); `run_tool` gives every tool a null stdin, its own process group, and polls with `waitid(WNOWAIT)`, so the group is killed before the leader is reaped. `MAX_MEDIA_SECONDS` (300) is the one analysis cap shared by audio, OCR frames, dish photos, and step moments.
- `src/media_worker.rs` — client for the persistent Python media workers (`pi/local-media.py serve`): one process per kind (transcribe, OCR), started lazily in its own process group, JSON lines on stdin/stdout. A kind serialises its requests; a timeout, a bad or oversized response, or an exit kills the group and drops the worker, and a worker that died after serving is replaced once. Transcription and OCR run concurrently.
- `src/embeddings.rs` — HTTP client for the EmbeddingGemma 2 sidecar (`llama-server --embeddings`, `EMBEDDING_URL`): `Embedder::embed(&[Input::{Text, Image, Audio}])` returns unit 768-d vectors, with a 300 s per-request timeout for media and background work, while `Embedder::interactive()` gives page requests (the search query and the inline index refresh) 10 s; `wait_until_ready` probes the sidecar every 30 s for up to 30 minutes; `blocking()` gives the ffmpeg threads a `BlockingEmbedder`; `document`/`query` add the model's retrieval prefixes; `to_blob`/`from_blob` store vectors as little-endian f32 BLOBs.
- `src/moments.rs` — video step moments: `capture` builds the moment pool during an import (12 s audio windows every 6 s, stills every 2 s, ≤ 40 frame vectors); `match_steps` aligns steps monotonically to audio when the narration clearly talks about the steps (mean lift ≥ 0.06), else to frames (in audio mode a weak step falls back to its frame match only when that lies between its neighbours' audio moments); `match_draft` / `refresh_recipe` store the result (`refresh_recipe` runs one refresh of a recipe at a time, so the last edit's moments win); `view` builds the page view (time, match source, stills). `capture` takes a cancel flag and stops between sidecar calls (chunks of 8) once it is set or the media deadline passes, keeping a partial pool.
- `src/search.rs` — library search over EmbeddingGemma vectors: `recipe_document` builds the text embedded per recipe (title capped at 200 bytes and body at 6000, so every document fits the sidecar's 8192-token context), `refresh_index` re-embeds only recipes without a usable vector or edited since their vector was built (`recipe_embeddings.updated_at` holds the recipe `updated_at` the vector was built from; when an edit left the document unchanged, the stamp is updated instead of re-embedding), `search` / `rank` score a `?q=` query (cosine plus a title bonus when the query's words are whole consecutive words of the title, at least 0.60, within 0.10 of the best, max 24). A search or Folders view (`refresh_user`) embeds at most 24 stale recipes inline and hands the rest, or a failed batch, to a background refresh; while a background refresh or the startup backfill is indexing a user (one `IndexingSlot` per user, plus a global flag during the backfill) it only counts them. `backfill` is the one startup task: it waits for the sidecar (`Embedder::wait_until_ready`), embeds the folder prototypes (`folders::warm`), then compares every recipe's document and embeds the stale ones, rebuilding every vector when the sidecar serves another model (it re-embeds the newest stored document; cosine < 0.95 means the model changed). BM25 is the backup: `keyword_terms` / `keyword_rank` score every word of each recipe, read fresh per search with no index (title counted 3×, stopwords dropped, words cut to a shared stem: plural s, final e, y→i; results score at least 25% of the best, max 24). No `EMBEDDING_URL` or a failing sidecar falls back to BM25 silently, never an error. `app_settings.search_engine` (`embeddings`, `bm25`, or `shared`/absent, which follows the account whose AI logins the user uses (`ai_account`); `keyword_search_selected`, `POST /settings/search-engine`, under Developer tools) makes BM25 run every search. On the home page the search runs as the user types through htmx attributes on the `data-live-search` form (`input changed delay:350ms`, `hx-sync` replace): it fetches `/?q=…`, swaps `#search-results` and (out of band) `#search-title`, and replaces the address bar URL (an empty query becomes `/`). Enter searches at once. Without JavaScript the form submits normally.
- `src/folders.rs` — library folders: the sign's **A–Z / Folders / Cuisines / Group** toggle (`app_settings.library_view`: `az`/absent, `folders`, `cuisines`, `group`; `POST /library/view`, `update_library_view`; Group is offered and applies only while the user is in a group, `group_view_selected`, and lists `recipes::group_cards`, every member's shared recipes with the owner's name on each ticket; out of a group it falls back to A–Z) and the recipe page's "Filed in" pill (`POST /recipes/{id}/filing`, `update_filing`). Recipes are filed by EmbeddingGemma against fixed lists, `DISH_FOLDERS` (15, each a handful of example dishes; a recipe goes to the folder whose two closest examples average best) and `CUISINES` (14 "Thai food" queries; under `CUISINE_MIN_SCORE` 0.60 or within `CUISINE_MARGIN` 0.010 of the runner-up is Other). The prototypes are embedded once per process (`folders::warm`, run by the startup task `search::backfill` once the sidecar answers) and compared with each recipe's `recipe_embeddings` vector on every view; a Folders view never waits for them: until they are ready it starts one background warm-up and files only pinned recipes. Nothing is stored but the cook's pins, `recipes.folder` / `recipes.cuisine` (empty means automatic; pinning keeps `updated_at` and records no version). A recipe with no vector yet, or every unpinned recipe without the sidecar, sits in "Not sorted yet". `/?folder=<slug>` opens one folder (dish and cuisine slugs are distinct; `unsorted` follows the current view); a search that names a folder (`match_query`: "thai", "Thai food", "dessert", "pork") lists that folder's recipes before the ranked results. Tuned on 55 test recipes against the live sidecar: dish folders 47/55, cuisines 45/48. Changing a folder's examples changes the filing; re-measure before editing them.
- `src/htmx.rs` — htmx glue and the cookie helpers: `cookie_values(headers, name)`, `set_cookie(name, value, max_age)` (every cookie the app sets, session, accounts, flash, and display, is built here, so a change to the attributes is one edit), and `sets_cookie(headers, name)`; the `recipe_flash` one-time notice cookie (`flash_redirect(to, key)` / `flash_cookie(key)` set it, the `Flash` extractor reads it, keys are short lowercase words), `finish_popup` (see the sign-in popup below), `htmx_layer` (outermost layer on every route: clears the flash on the first successful HTML page, sends `HX-Push-Url: false` for a non-GET htmx request answered with a page, and retargets htmx error pages to `.app-shell`), and `full_page_redirect` (`HX-Redirect` for htmx requests, 303 otherwise; the auth middleware uses it for `/login` and `/setup`).
- `src/display.rs` — per-browser display mode: the `recipe_display` cookie holds `colour` or `eink`; no cookie means Automatic, which picks e-ink when the User-Agent contains "Kindle". Every page links `/display.css` after `app.css`; `display_css` (outside auth, `Cache-Control: no-store`) answers an `@import` of `static/eink.css` in e-ink mode and an empty sheet otherwise. `/settings/display` (`display_page` / `update_display`) saves or clears the cookie.

- `src/groups.rs` — groups, email invites, AI-login grants, and the recipe Share toggle, with the SQL on `account_groups`, `group_members`, `group_invites`, and `group_invite_sends` (grants are read and written through `settings.rs`, recipe queries through `recipes.rs`). `Invites` (`AppState.invites`, built in `main()` from `RESEND_API_KEY`, `RESEND_FROM` (default `Recipe Repository <invites@mail.reciperepository.app>`), and `PUBLIC_BASE_URL`) holds the `Mailer` (`Off`, `Resend` through `resend-rs` with a 15 s reqwest client, and in tests `Fake` / `Failing`) and the link base (`PUBLIC_BASE_URL` without a trailing slash, else `http://` + the request's Host). `send_invite` (`POST /settings/group/invite`) checks the address (`valid_email`), the daily limit (`MAX_INVITES_PER_DAY` = 20, counted in `group_invite_sends`, so cancelling frees nothing), stores the invite (token: 32 random bytes in base64url, of which only the SHA-256 is kept; the address only masked by `mask_email`, `j***@example.com`, and hashed, so inviting the same address again replaces the earlier link), then mails it, or with mail off or failing shows the link once: it answers with the Settings page itself (`crate::settings_view` with `GroupExtras`) rather than a redirect. Invites last 7 days (`INVITE_DAYS`) and are pruned with the hourly draft prune (`prune_invites`, which also drops sends older than a day). `cancel_invite`, `leave` (`leave_group_in`: the leaver's grants both ways go, its recipes stop being shared, and a group left with one member is deleted, that member's recipes unshared too), `update_ai_grants` (`grantee` fields; adding a grant needs `own_ai_configured`, taking one back never does), and `update_ai_source` (`app_settings.ai_source`, which granter a user uses when several share) are Settings handlers flashing into `settings-group`. The invite routes: `invite_page` (`GET /invites/{token}`, outside the middleware, standalone `invite.html` like `login.html`; states `gone`, `signed_out` (Sign in with `next`, or Create account), `accept`, `own`, `member`, `other_group`, `declined`), `accept_invite` (`POST /invites/{token}/accept`, protected; `accept` joins in one transaction, creating the group with the inviter when the inviter has none, and refuses an account already in another group), `decline_invite` (outside, anyone with the link), and `signup_through_invite` (outside; `auth::add_user`, then `accept`, then `auth::sign_in_browser`, landing on `/settings#settings-group`). `ai_dependents` names the members whose `ai_account` is a given account (the delete-account warning). `update_share` (`POST /recipes/{id}/share`, owner only, refused outside a group when sharing) flips `recipes.shared` through `recipes::set_recipe_shared` without touching `updated_at` or versions.

**AppState** is `Arc`-shared into every handler: `db: SqlitePool`, `model` (the `PI_MODEL` default), `pi_worker_path`, `auth_script_path` / `claude_auth_script_path` (the Codex and Claude sign-in helpers), `search_grounding: bool` (`PI_SEARCH_ENABLED`), `codex_flows` / `claude_flows` (in-flight sign-in flows by flow id, each with its user; expired Codex flows are pruned whenever a new one starts), `model_catalogue` (the last model listing per source, a pi provider id or an endpoint id), `media_debug_runs` (video import and debugger runs, `ai::DebugRunMap`), `thumbnail_jobs` and `moment_jobs` (in-flight background runs per recipe id), `embedder: Option<Embedder>` (`None` turns off search, step moments, and dish-photo ranking), `rate_limits: Arc<auth::RateLimits>` (the brute-force counters; in memory only, so a restart forgets them), and `invites: groups::Invites` (the mailer and link base; tests use `Default::default()`, mail off).

Front end (load-bearing): every page is still a whole server-rendered document; htmx 1.9 makes it feel like an app. `base.html` loads `/static/htmx.js` and `/static/app.js` (both `defer`, both build outputs) and puts `hx-boost="true"` on `<body>`, so local links and forms fetch the next page with XHR and swap the body in place, push the URL, and update the title. Config lives in the `htmx-config` meta: `historyCacheSize: 0` (no page snapshots in localStorage, since another account may use the browser; Back refetches), `allowEval` and `allowScriptTags` off (no inline scripts anywhere — all behaviour lives in `web/src`). Opt out with `hx-boost="false"` where a whole page must load: the account menu, sign-out, account creation, the display form (its stylesheet is in `<head>`), photo upload and the add-note form (multipart), edit-block links, their forms' Cancel links (`data-edit-cancel`: `recipe.ts` resets and hides the form and returns focus to the block, so the `data-poll-unless-editing` pollers run again), and still links (JavaScript handles those; note photos open in the same still viewer). Status notices never go in the query string: a mutating handler answers `flash_redirect("/page#block", "key")` and the page maps the key to text (Settings shows each notice inside its own block, ids `settings-ai`, `settings-cleaner`, `settings-web-search`, `settings-units`, `settings-moments`, `settings-chat`, `settings-account`, `settings-search`, `settings-group`; the `#fragment` only matters without JavaScript; the invite form is the exception that answers with the page itself, so a link made without mail shows once). Settings forms swap just `#settings` (`hx-select`/`hx-target`, `show:none` keeps the scroll); recipe block forms swap the body with `show:none`; the filing form swaps only `.filing-disclosure` and the Share-with-group form only `.share-toggle`; chart links swap `.paper` with `hx-replace-url`. The library's view toggle, folder stacks, and links back out of a folder swap `#all-recipes` with `hx-replace-url="/"`, so the address bar stays at `/` and no history entry is added; `/?folder=<slug>` remains for plain HTML and direct links. `library.ts` keeps the open folder (`data-open-folder` on `#search-results`) in `sessionStorage`, so Back and refresh reopen it; a library page without one, such as the Recipes link, forgets it. Background work is polled with hidden `hx-trigger="every 3s"` pollers (`hx-indicator="this"`): `data-poll-unless-editing` skips a tick while an edit (or a note's Edit form) is open, and `data-swap-when-gone="<selector>"` holds the swap until the marker is gone from the response (the step-moments poller waits for `[data-moments-pending]` to go, the dish-photo poller swaps `.thumb-manage` once `[data-thumb-pending]` is gone, and the chat drawer's poller names its current `data-chat-state` token, the pending answers' ids, so it swaps once an answer lands). The chat drawer's question form, Clear, Deny, and poller swap only `#recipe-chat`; Accept reloads the body. Errors (4xx/5xx) are swapped into `.app-shell`. Codex and Claude sign-in opens in a popup on Settings (`auth-popup.ts`): Reconnect / Connect `hx-get` the sign-in page's `#auth-flow` into `#auth-popup-body` (the links set their own `hx-target`, `hx-select`, and `hx-swap`, so they do not take the provider form's `#settings` swap; `dom.ts`'s `keepTabWithin` keeps Tab focus inside the popup, as in the still viewer), the flow's forms and links swap `#auth-flow` (so the page also works on its own), and a finished step answers `htmx::finish_popup` (204 + flash + `HX-Trigger: popup-finished`), which closes the popup and refreshes `#settings`. When htmx fails to load, `app.js` wires the page once and everything works as plain HTML.

Data flow: HTTP request → handler (extractors `State<Arc<AppState>>`, `Path`, `Form`, `Query`) → sqlx helpers or the AI pipeline → Askama template struct → HTML. Every page is a server-rendered template in `templates/`; forms post `application/x-www-form-urlencoded` via axum `Form`.

Accounts (load-bearing): the browser holds the active session's token in `recipe_session` and the tokens of its other signed-in accounts in `recipe_accounts` (joined with `.`, same cookie attributes and lifetime). `browser_sessions` resolves both to live sessions, active first, one per user; `recipe_accounts` is read for at most 7 tokens (`MAX_BROWSER_ACCOUNTS` − 1). The middleware drops ended tokens from `recipe_accounts`, and when the active session has ended it promotes the first remembered one. Signing in (`login`, `create_account` → `sign_in_browser`) makes the new session active and keeps the others behind it (an older session of the same user on this browser ends). `POST /accounts/switch` swaps the active token with a remembered one and opens `/`; any other id, an existing account or not, goes to the plain `/login`. The account menu (`load_account_menu`) reads usernames only for the browser's own sessions, so a signed-in user cannot list the server's other accounts through it. `POST /logout` ends only the session in `recipe_session` and hands the browser to the next remembered account (else `/login`); when that session had already ended elsewhere, every remembered account stays signed in and the first takes over. `POST /logout/all` ends every session the browser holds. `POST /settings/delete-account` (`delete_account`, `hx-boost="false"` like the account menu) deletes only the active account: it hands the browser to the next remembered account and opens `/` (flash `account_deleted` on the library), or clears both cookies and opens `/login` (same notice; `/login` goes on to `/setup` when no account is left). The confirmation page (`GET`, which never deletes) warns when group members generate with this account's AI logins now (`groups::ai_dependents`): it names them, and says each falls back to another member's shared logins or needs its own. The account menu reaches templates through the `ACCOUNT_MENU` task-local, not template fields: pages outside the middleware (`login.html`, `setup.html`, `invite.html`, or anything rendered on a spawned task) get no menu. AI logins are shared per member within a group: `ai_account(db, user_id)` resolves the account whose provider, subscriptions, endpoints, models, effort, video cleaner, search key, and `search_engine = shared` serve a user: the user's own when it has an AI setup of its own (`own_ai_configured`: its active provider is a connected subscription or one of its endpoints with a key); else that of a group member who granted it theirs (`ai_grants`, counted only while granter and grantee are both members of the grant's group), the one picked in `app_settings.ai_source` first, then the earliest grant, skipping granters with no AI setup either; else its own (which then fails as `AiNotConfigured`). Resolving again returns the same account. Migration 0026 replaced the old instance-wide rule (the first account's logins for everyone unless `app_settings.ai_logins = "own"`; that key and `POST /settings/ai-logins` are gone). Generation entry points (`ensure_ai_configured`, `pi_recipe`, `ensure_media_cleaner_configured`, `clean_media_evidence`) resolve it first, so a shared subscription's refreshed token is stored back on the owning account. Settings shows an account using a member's logins only a summary of that setup (never its keys) above its own provider form (connecting one makes it win), and hides its own cleaner and search-key blocks; the edit handlers always act on the signed-in user's own setup. `app_settings` is keyed by `(user_id, key)`, so every settings accessor (`ai_provider`, `selected_model`, `selected_effort`, `step_moments_enabled`, `media_cleaner_setting`, …) takes the user id; `reconcile_ai_provider` heals each user's value against that user's own endpoints.

Auth flow (load-bearing): every library route sits behind `auth_middleware` (`from_fn_with_state` on the `protected` router; `/setup`, `/login`, `/logout`, `/logout/all`, `/healthz`, and the invite link routes `GET /invites/{token}`, `POST /invites/{token}/decline`, and `POST /invites/{token}/signup` are outside it). A valid `recipe_session` cookie → the user id is inserted into request extensions as `AuthUser`, which handlers take as an extractor. No valid session and no `users` row → redirect to `/setup`; no valid session otherwise → 303 to `/login` (a GET carries its path and query in `?next=`, other methods go to `/login` plain). `POST /login` matches the username ignoring ASCII letter case (`COLLATE NOCASE`, the rule usernames are unique under; a username may not contain control characters) and checks the password against `users.password_hash` with Argon2 (an unknown username costs the same dummy check), then creates a session and redirects to `next` only when it is a local path (`local_target` refuses `//host`, `/\host`, and absolute URLs). Brute-force limits (load-bearing, `auth::RateLimits` in `AppState.rate_limits`, sliding windows held in memory): before the database or Argon2 is touched, every `POST /login` takes one hit on its client address (`Limit::LoginAddress`, 30 per 15 minutes) and its username (`Limit::LoginUsername`, `username_key`: trimmed, ASCII-lower-cased like `NOCASE`, 10 per 15 minutes, known and unknown usernames alike) in one step under the lock (`attempt`); a key at its allowance answers 429 with the sign-in form and "Too many sign-in attempts. Try again in N minutes." (the same page whether the username exists). A success clears the username's hits and takes back (`forgive`) only its own address hit. `POST /settings/password` takes a `Limit::Password` hit per user (10 per 15 minutes, cleared by the right current password), and `POST /accounts/new` allows 10 accounts an hour per address (`Limit::NewAccount`; a username refused as taken counts too, other form errors do not), checked before hashing. `/setup` is not limited (it creates only the first account). The map holds at most `MAX_LIMIT_KEYS` (10,000) keys: a new key past the cap first drops every fully expired key, then the least recently hit. The client address (`ClientAddress` extractor) is the connection's peer address (the server runs `into_make_service_with_connect_info::<SocketAddr>()`), or with `TRUST_PROXY_HEADERS` the left-most `X-Forwarded-For` entry; IPv6 counts per /64 (`address_bucket`). A router served without connect info (the tests) has no address, so the per-address limits are skipped and the per-username and per-user ones still apply. Sessions live in the `sessions` table: the cookie holds 32 random bytes (base64url), and the table holds only their SHA-256 (`token_hash`). A session ends 30 days after its last use. The middleware extends it at most once a day and then sends the cookie again with `Max-Age` of 30 days. A cookie the middleware sends (that extension, a promotion, or the accounts-cookie cleanup) is dropped when the handler's response already sets that cookie (switch, password reset, account deletion), so the handler's choice wins. The cookie is `Path=/; HttpOnly; SameSite=Lax` (`htmx::set_cookie`) and has no `Secure` flag, because the app serves plain HTTP on the LAN. `SameSite=Lax` still sends the cookie with a form posted from another port on the same host (same site, different origin), so `auth::same_origin_only` (a layer on every route, just inside `htmx_layer`) refuses any request other than GET/HEAD/OPTIONS that came from another origin, as Go's `CrossOriginProtection` does: `Sec-Fetch-Site` must be `same-origin` or `none` when present, else `Origin` (scheme ignored, so a TLS proxy in front works) must match `Host`; a request with neither header passes. A refusal is `AppError::CrossOrigin` (403). `POST /logout` deletes the session row and clears the cookies when no remembered account is left (see Accounts above). `POST /settings/password` re-verifies the current password, then replaces the hash, deletes all of the user's sessions, and issues a new one in one transaction (the single password page is "Reset password" at `/settings/password`, linked from the Account block in Settings). Setup signs the new account in the same way. Account deletion (`delete_user`) runs in one transaction: first `groups::leave_group_in` (grants to and from the account go, and a group left with one member is dissolved), then `recipe_thumbnail_candidates` and `draft_thumbnails` (no foreign keys), `ai_drafts` of the user, `recipe_notes`, `recipe_chat_messages`, `recipes`, `app_settings`, `ai_endpoints`, `pi_credentials`, `sessions` explicitly, then `users`; cascades take the rest (blocks, step ingredients and step moments, sources, versions and counters, embeddings, moment pools, draft moments, and any table keyed to `users(id)` with `ON DELETE CASCADE`: `group_members`, `ai_grants`, `group_invites` the account sent, `group_invite_sends`). A new per-user table without such a foreign key MUST be added to `delete_user` and to `OWNED_TABLES` / `seed_account` in `src/tests/auth.rs`. The handler then drops the account's in-memory state: model catalogues of its endpoints, its recipes in `thumbnail_jobs` / `moment_jobs`, its Codex and Claude sign-in flows, and its import and debugger runs (`ai::forget_media_runs`). Recipes it shared go with it, since access to a shared recipe is always derived from the live row and membership. A dish-photo run that outlives its recipe stores nothing (`store_recipe_thumbnails` checks the recipe), and a video import that outlives its account stores no draft (`create_draft` inserts only while the user exists). The `users` table is the single source of truth — never a config file.

AI flow (load-bearing): Add recipe is one card (`templates/add_recipe.html`, `/recipes/new`) whose single prompt posts to `POST /ai/generate`; `route_prompt` sorts its links. A link `canonical_social_url` accepts (a Facebook/Instagram video, anywhere in the text) starts a video import (`start_import`, with the card's Video options tick boxes; a post without `video_options` reads every channel), and the rest of the text, other links included, becomes the notes. Two different videos are refused on the card, and any refusal re-renders the card with the prompt as typed. `web/src/add-recipe.ts` pins each link under the card as a slip, sorted by the same rules (keep the two in step), and shows Video options only while a video is linked. `/ai/import` only redirects to the card. Without a video, `POST /ai/generate` → `create_draft` → `pi_recipe` → `resolve_backend` → `RecipeBackend::run`, which runs `node pi/recipe-worker.ts` on a blocking thread (`run_worker`, at most `AI_WORKER_CONCURRENCY` (2) workers at once; one JSON request on stdin, one JSON line on stdout). A subscription run (`run_subscription_worker`) goes on in a tokio task of its own, so a dropped request cannot abandon it; it holds its credential's slot (`acquire_subscription_worker(user_id, pi_provider)`: runs on the same login take turns, other logins run alongside) and hands the worker a **per-request `0o600` temp `auth.json`** (`TempAuthFile`, removed on drop) materialized from the DB credential; a token the worker refreshed is written back by `store_refreshed_pi_credential`, only over the credential the run started from. `run_with_retry` is the one decode-and-retry loop for generation, the chat, and the video cleaner: a retryable worker failure or a reply its caller refuses (for a recipe, one that fails `validate_generated`) gets one more attempt; a missing or refused login never does. The result lands in `ai_drafts` with `expires_at = now + 24h`; `recipes::delete_expired_drafts` (candidates first, then the drafts, in one transaction) runs before each draft insert, at startup, and every hour (`prune_expired_drafts`). The preview page shows the draft; its alteration box (`alter_draft`) makes another draft from it, carrying the dish-photo candidates and the moment pool along the chain, and `apply_draft` always creates a new recipe, deleting the draft in the same transaction, so a second Save of a consumed draft saves nothing and shows the expired page. Drafts never change a saved recipe; the recipe chat is the only AI path that does. The active provider is `app_settings.ai_provider`: `"pi"` (Codex), `"claude"` (the Claude subscription), or an `ai_endpoints` row id; a subscription counts as connected once any credential is stored for it (`pi_authorised`, the same test as `ensure_provider_configured`). `resolve_backend` turns the value into `RecipeBackend::Subscription` (the Pi SDK path) or `RecipeBackend::Endpoint`, whose run sends the spec, base URL, key, and model to the worker — the key never round-trips back. Specs: `openai` (Responses API) and `anthropic` (Messages API) run the worker's own code, with native web search only when the endpoint's base URL is the native preset's (`endpoint_has_web_search`: `https://api.openai.com/v1`, `https://api.anthropic.com`; a custom Anthropic-compatible server writes without research, and Settings marks its row so); every other spec is a pi-ai built-in provider id (`google`, `mistral`, `xai`, `deepseek`, `openrouter`, `groq`, `together`, `fireworks`, `cerebras`, using pi-ai's catalogue and base URL, so `base_url` is stored empty) or `openai-compatible` (a custom Chat Completions server, key optional). An endpoint without web search runs every generation with search off (`endpoint_search_mode(spec, base_url, mode)`), so a grounded request is written from knowledge and a video import uses `EVIDENCE_OFFLINE_RECIPE_PROMPT`; `PI_SEARCH_ENABLED=false` does the same for every backend, video imports and their alterations included (`generation_search_mode`). Settings adds a provider from `PROVIDER_PRESETS` (pick a provider, paste a key; only the two "Other server" choices, OpenAI- and Anthropic-compatible, ask for a URL and a model) and makes it active. An endpoint key must pass `header_safe_key` (printable ASCII without spaces, at most 4096 bytes), and a custom server URL must parse as http(s) with a host; it is stored as the URL parser writes it, without a trailing slash (`normalise_url`). The video cleaner (`cleanMedia`) runs through the same backends (`resolve_backend`): `app_settings.media_cleaner_provider` (empty follows `ai_provider`) and `media_cleaner_model` (empty uses the provider's model); `0016_media_cleaner_provider.sql` turned the old Vercel AI Gateway credential into an `openai-compatible` endpoint.

Key invariants:

- Shared recipes: a recipe is readable by its owner, or by a member of the owner's group while `recipes.shared` is set (`recipes::READABLE_BY_VIEWER`, bound as `?1`, so queries using it bind only numbered parameters). Only `recipe_page` (through `find_readable_recipe`, which renders `recipe.html` read-only with `shared_by` set: card, chart, scaling, sources, photo, step moments by the owner's switch; no edit, chat, notes, versions, filing, photo tools, moments capture, or delete), the dish photo and still handlers (`find_recipe_thumbnail`, `find_recipe_still`), the Group view (`group_cards`, `attach_ingredients`), and `copy_recipe` (`POST /recipes/{id}/copy`: details, blocks, step ingredient lines, sources, photo, and chart into a new recipe of the viewer; never notes, chats, versions, or moments) use it. Every other recipe query stays owner-scoped (`find_recipe`, `user_id = ?`), so a member's POST to an owner tool answers 404. Access is never copied: leaving or dissolving a group ends it at once, and `leave_group_in` also clears `shared` on the leaver's recipes (and the last member's on dissolve), so a later group never sees them unasked. Toggling `shared` keeps `updated_at` and records no version. Search, folders, and cuisines cover only the user's own library.
- Groups and invites: an account is in at most one group (`group_members.user_id` is the key); a group exists only with two or more members. Invite tokens are stored only as SHA-256 (`group_invites.token_hash`), addresses only masked and hashed; logs and pages show only the masked address (`mask_email`), mail errors are masked before logging, and `RESEND_API_KEY` is never logged or rendered (`Mailer` has no `Debug`). Accepting proves the address, so `users` has no email column. `ai_grants` rows count only while both accounts are members of the grant's group, and `leave_group_in` deletes the leaver's grants both ways. A new per-user group table MUST cascade on `users(id)` and join `OWNED_TABLES` / `seed_account`.
- AI output must pass `validate_generated` (a title, at least one and at most 100 named ingredients, 2 to 100 steps, each with text and a `chartLabel` and a timer of 0 to 7 days; every ingredient used at least once and at most once per step, so one ingredient may be split across steps; `inputSteps` only reference earlier steps, and every step but the last feeds exactly one later step, …) before any draft is saved. Output that fails it is retried once.
- `recipes.chart_json` is AI-derived only; any manual block edit MUST call `invalidate_chart` (clears `chart_json`, so the viewer falls back to linear inference) and `touch_recipe` (stamps `recipes.updated_at`). Every change to a recipe's title, description, or blocks MUST bump `updated_at`: the chat's `proposal_base` staleness guard and the search index compare it, so an edit that skips it is overwritten by a stale proposal and missed by search until the next startup backfill. `update_recipe`, `restore_version`, and `accept_chat_proposal` set `updated_at` in their own UPDATE.
- Dish thumbnails come only from two local paths — the ffmpeg scoring pipeline during an import, or a user-uploaded image normalised through ffmpeg on the recipe card (a JPEG ffmpeg cannot convert is kept as uploaded) — never a cloud service. Draft candidates live in `draft_thumbnails` and recipe re-pick candidates in `recipe_thumbnail_candidates`; both MUST die when consumed (apply/choose/remove/discard/expiry; expired drafts and their candidates go within the hour, `delete_expired_drafts`). Only chosen JPEGs are copied into `recipes.thumbnail_jpeg`. Thumbnail bytes are served exclusively to the owning user and never logged. In-flight re-pick runs are tracked only by the in-memory `AppState.thumbnail_jobs` set, so a restart drops "pending" back to idle.
- The subscription credentials (Codex and Claude) are DB-only; Pi SDK invocations MUST go through `run_subscription_worker`, which hands the worker a per-run `TempAuthFile`, never a fixed-path credential file.
- Endpoint API keys live in the `ai_endpoints` table, never in env or config; templates only ever receive the masked tail (`mask_key`), and the add/switch/delete handlers (`add_endpoint` / `update_settings` / `delete_endpoint`) are the only mutators. Deleting the active endpoint falls `ai_provider` back to `"pi"`; `reconcile_ai_provider` heals stale values at startup.
- Refused logins: the worker reports an OAuth refresh the provider rejected, a 401 (for Codex also read from the HTTP status and from its token wording: `token_expired`, an expired or invalidated authentication token, "try signing in again"), or an invalid key as `code: "auth"` (`isAuthFailure` / `workerFailure` in `pi/recipe-worker.ts`). `ai::track_login` (wrapped around every subscription and endpoint worker run) stamps `pi_credentials.auth_failed_at` / `ai_endpoints.auth_failed_at` and returns `AppError::AiLoginRefused` (never retried; the error page and the import page link to Settings); a run that signed in or a reconnect (`store_pi_credential`) clears it, and a stored token refresh (`store_refreshed_pi_credential`) does not. A subscription `listModels` does not prove the login, so it never clears the flag. Settings shows "Sign-in expired" / "Key rejected" on the row and offers **Refresh sign-in** (`POST /settings/check/{codex|claude}`, the worker's `checkLogin` → `CheckLoginResponse`, which forces an OAuth refresh) and **Test key** (`POST /settings/endpoints/{id}/check`, a model listing); both flash `*_login_works` / `endpoint_key_works`, `login_refused`, or `login_check_failed` into the AI block.
- LLM call logging: every worker call through `run_with_retry` (generation, chat, video cleaner) logs the full request (provider, model, attempt, prompt, system prompt) and the full response (the reply JSON, elapsed ms) at `info` level, and the Pi worker's stderr is forwarded into the app log after every run (a sign-in helper's only after a failed or timed-out run), so `docker compose logs` shows the whole call. Only selected fields are logged — `apiKey`/`authPath` never appear.
- Notes: every `recipe_notes` query is scoped by `user_id` and `recipe_id`; note photos are local like dish photos (ffmpeg-normalised uploads only), served only to the owner, and never logged. The chat sends notes to the worker in the request's `library` (the newest 40 notes, the newest 6 photos as base64, the newest 12 versions plus any a note names); the host log shows the notes' text and `photoSent` flags through `ai::chat_library_log`, never photo bytes, and the worker logs each tool call by name and arguments.
- Recipe chat: every `recipe_chat_messages` query on a thread is scoped by `user_id` and `recipe_id` (only the startup recovery and account deletion reach across threads), so a thread is only ever read, answered, accepted, or cleared by the account that wrote it (another account gets 404). The chat's edit tools never write a recipe: they change a copy in the worker, and only the cook's Accept writes it (`accept_chat_proposal`: staleness guard on `proposal_base`, version history, divider, moments refresh, chart dropped on block changes like any manual edit). Answers left `pending` by a restart are failed at startup (`fail_interrupted_chats`). The user's `app_settings.recipe_chat` switch (`chat_enabled`, default on; `POST /settings/recipe-chat`) hides the drawer and 404s its routes. In SQL, never mix `?` and `?N` placeholders in one query: sqlx binds the unnamed ones out of order.
- Web search in the recipe chat: with `PI_SEARCH_ENABLED`, `ai::chat_web_search` sends `searchMode: gapfill` (search allowed, never required), and the model gets one `search_web` function tool (not `web_search`, the name of Anthropic's server tool, which drew empty `tool_use` turns from Claude), at most 3 searches per answer (`CHAT_SEARCHES`; a call without a query does not count). When the backend has web search of its own (`chatSearchPayload`: Codex and OpenAI endpoints get the hosted Responses `web_search`, the Claude subscription and Anthropic endpoints `web_search_20250305` with `max_uses` 4 per request, so an answer can run up to 3 × 4 server searches), `answerChat` answers each call with `hostedSearchAnswer`: a separate one-shot request through the same model at reasoning `low` with only the hosted search tool, whose text (cite tags stripped) becomes the tool result; a search answer cut off at the output limit is kept and marked as cut off. The chat loop itself never carries hosted search items: pi-ai drops them (`web_search_call`, `server_tool_use`, `web_search_tool_result`) when it replays a turn, and Claude can end a search turn with `stop_reason: tool_use` and no usable block. A failed, paused (`pause_turn`), or empty search is a `WebSearchError`, an error result the model answers around. Every pi-ai provider instead answers `search_web` through the AI account's search API key (`apiSearcher`, run by `runSearchTool`; `web_search_keys`, one per account, shared with AI logins like everything else in the AI setup); without a key such models get no search tool. `pi/web-search.ts` holds one adapter per search API in `SEARCH_PROVIDERS` (Brave, Exa, Tavily), each mapping its results to `{title, url, snippet}`; adding one is an adapter there plus its key in `WEB_SEARCH_PROVIDERS` in `main.rs` (no migration). Search keys, like endpoint keys, must be printable ASCII without spaces (checked on save by `header_safe_key`, at most 4096 bytes, and again in `webSearch`), and `redact` strips the key from any error text. The key, like endpoint keys, reaches templates only masked and is never logged; Settings edits only the signed-in user's own key (`POST /settings/web-search`, `/settings/web-search/delete`) and shows a sharing account a one-line summary. The worker reports the path taken as `ChatResponse.search` (`hosted`, `api`, `none`), and logs a reply it could not read in full (`chat reply unreadable`).
- Passwords are stored only as Argon2 hashes (`users.password_hash`); `reset_password` MUST verify the current password first and never log or return password material. Session tokens are never stored or logged: `sessions` keeps only `token_hash`.
- The embedding sidecar is the only place images, audio windows, and text are embedded; it runs on the same host (compose service `embeddings`), so frames never leave the machine. Every embedding feature degrades when it is absent: search falls back to BM25, imports skip the moment pool, dish photos keep the heuristic order, and library folders hold only pinned recipes (the rest wait in "Not sorted yet").
- The video moment pool (`draft_moment_vectors`, `draft_moment_stills`) rides with the draft (FK cascade on `ai_drafts`), is copied along alteration chains, and `apply_draft_moments` moves it to `recipe_moment_vectors` / `recipe_moment_stills` inside the apply transaction before the draft row is deleted. A recipe saved without a pool gets one from `POST /recipes/{id}/moments/capture` (`start_moment_capture`): a background run downloads the social video again (`extract_fresh_moment_pool`), `store_recipe_moment_pool` replaces the pool, and `refresh_recipe` matches the steps; `AppState.moment_jobs` tracks the run in memory only. `recipe_step_moments` is keyed by step block id (moves keep it, deletes cascade); every block mutation calls `moments::spawn_recipe_refresh`. Stills are served only to the owning user. The user's `app_settings.step_moments` switch (`step_moments_enabled`, default on) gates capture and display for that user's recipes and drafts.
- Media extraction: transcription and OCR evidence is delivered before thumbnails and the moment pool, so the cleaner and draft calls run while those finish; the extraction job always removes its work directory before it releases the media permit, and dropping `PendingExtras` cancels the moment stage, mid-stage included (`moments::capture` checks the flag between sidecar calls). Disk budgets: the work directory is measured once, after the download lands (160 MiB); the OCR lane then checks only its own `frames/` (128 MiB) and deletes them when over; the WAV needs no check. OCR cleaning keeps a few small word lists and no others: `OCR_UNITS` (one list of measure and time units, shared by the token gate, attached quantities like `200g` / `10min` / `1½cups`, and the context that keeps a bare number), quantity context words (count nouns and ingredients), the short words allowed under 3 letters (`is_short_ocr_word`), the readability anchors of one-sample cards (`has_readability_anchor`), `OCR_JOINED_PAIRS` (which only restores a missing space and never rewrites a word or brand), and the all-caps duplicate-word drop in `repair_ocr_spacing`; vulgar fractions (½, ¾, ⅓, …) count as digits. Precision comes from row confidence plus corroboration across frames (a row needs two samples; a one-sample card needs standalone strength). Never feed the caption to Whisper as `initial_prompt` or `hotwords` (measured: the transcript collapses). Page titles that embed the caption are reduced to the account (`account_title`); `MediaEvidence.audio_segments` is `#[serde(default)]` so stored evidence stays readable.

## Development Commands

All development, benchmarking, experimentation, dependency/package installation, builds, and testing MUST run inside Docker. Do not run Rust, Node, Cargo, npm, benchmark, or packaging/install commands directly on the host machine. Use the project Docker/Compose environment (or an equivalent disposable development container) so the local machine is not modified by toolchains, caches, dependencies, or generated artifacts.

```sh

docker compose run --rm <service> <command>  # run build, test, fmt, clippy, benchmarks, or installs in a container

```

Do not start the app stack by hand: no bare `docker compose up` or `./deploy-local.sh`. To run or check the app, deploy it to minibuntu with `./deploy.sh minibuntu` and check `http://minibuntu:3000/healthz`; on minibuntu itself that deploys to the local daemon. `deploy.sh` is gitignored (host-specific), so a fresh checkout has none. ## Code Conventions & Common Patterns

- **Handlers**: `pub(crate) async fn` free functions, `State<Arc<AppState>>` first, returning the crate alias `type Result<T> = std::result::Result<T, AppError>`. Page-render handlers are named `*_page`; mutators follow `update_/delete_/add_/move_/alter_/apply_/cancel_*`.
- **Errors**: one `AppError` enum (thiserror) in `main.rs` with a single `IntoResponse` mapping — `NotFound`→404, `BadRequest`→400, `CrossOrigin`→403, `TooManyRequests`→429 (a brute-force limit; the limited forms re-render themselves with its `user_message` instead), everything else→500 (`AiNotConfigured`, `MediaCleanerNotConfigured`, `AiLoginRefused`, and `CodexAuth` / `ClaudeAuth`, "Sign-in did not work" with the helper's reason, link to Settings). `AppError::user_message()` is the reader-facing text: `GENERIC_FAILURE` for `Internal`, `CodexAuth`, `ClaudeAuth`, `Database`, and `Template`, else the error's own text; pages that show a failure inline (the Add card, draft page, import page, debugger) use it and log the error once. Extend `AppError`, never introduce per-module error types. Log once at the boundary: `error!(error = %self, "request failed")`.
- **SQL**: sqlx 0.8 raw queries (no `query!` macros), row types via `#[derive(FromRow)]`, multi-step writes inside a transaction opened by `recipes::begin_write` (`BEGIN IMMEDIATE`, never `pool.begin()`) and passed as `&mut sqlx::Transaction<'_, sqlx::Sqlite>`. Accessors live in `src/recipes.rs` (recipes, blocks, versions, drafts, thumbnails, moments, the search index, chat threads, notes) and `src/settings.rs` (`app_settings`, `pi_credentials`, `ai_endpoints`, `web_search_keys`); `auth.rs` keeps its own queries on `users` and `sessions` and the account-wide setup and deletion, and `ai.rs` writes `ai_drafts` and the new recipe in `create_draft`, `apply_draft`, and `cancel_draft`. Put new queries with their table's accessors.
- **IDs & timestamps**: `Uuid::new_v4().to_string()` TEXT PKs; timestamps are RFC3339 strings via `stamp()`. Do not introduce INTEGER ids or epoch timestamps.
- **Config**: `dotenvy::dotenv().ok()` with defaults read in `main()`; boolean switches via `env_bool(name, default)` (`PI_SEARCH_ENABLED`, `THUMBNAILS_ENABLED`, `MEDIA_OCR_ADAPTIVE`, `TRUST_PROXY_HEADERS`), which reads 1/true/yes/on and 0/false/no/off in any case and keeps the default when unset or anything else; user-visible settings persist in the `app_settings` key/value table, not env.
- **Async**: `#[tokio::main]`; blocking Node subprocess work inside `tokio::task::spawn_blocking` with plain `std::process::Command` (`ai::run_node`, which kills a run past its timeout).
- **Logging**: `tracing` + env-filter; `info!`/`warn!`/`error!`; HTTP via `TraceLayer`.
- **Templates**: Askama structs with `#[template(path = "...")]`; new pages extend `templates/base.html`; `{% match %}` for Rust Option/enum rendering.
- **Shared types** (serde, camelCase renames for AI wire types) live in `main.rs` — keep them there, not in feature modules.
- Form validation helpers in `main.rs`: `required(s, name)`, `trim`, `number(s)`.

- Migrations run via compile-time embedded `sqlx::migrate!()`; any schema change is a new numbered `migrations/000N_*.sql`.
- **Browser code**: TypeScript in `web/src`, compiled to ES5 because older Kindle browsers parse nothing newer. Only the ES5 library is visible to the type checker, so `Promise`, `Array.from`, `String#includes` and the like fail the build; the DOM lib still declares `NodeList.forEach`, `Element.closest` and `matches` without the webkit fallback, so use the `dom.ts` helpers instead. A feature registers with `onPage(root => …)` and must find its elements inside `root` (it runs on the first page and on every swapped-in fragment; `firstTime` guards double setup); long-running loops stop once their element is no longer attached. Delegated `document` listeners are registered once. htmx is pinned at `htmx.org` 1.9.12 (dev dependency; 2.x drops the older browsers).
- `.agents/` skills are coding-agent tooling, excluded from the Docker image.
