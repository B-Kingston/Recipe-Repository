# Repository Guidelines

## Project Overview

Kindle Recipes is a deliberately small recipe library for Kindle browsers and ordinary desktop browsers. It is a single Rust/Axum process: Askama renders every page server-side, SQLite holds all data, and an OpenAI Codex (Pi) Node worker generates recipe drafts through the user's ChatGPT subscription.

Access control is per account with a native sign-in page: the first visit redirects to `/setup` to create the first username and password (stored as an Argon2 hash in SQLite), and setup signs the browser in. Every library route then requires a session: a signed-out visitor goes to `/login`, and a successful sign-in sets an `HttpOnly` session cookie. Each account has its own library, drafts, and settings; AI logins (subscriptions and API keys) are the first account's, shared with every other account until it chooses its own in Settings. The account avatar at the right of the header opens the account menu (`<details>` in `base.html`): it lists every other account on the server, switches at once to one this browser is already signed in to, links the rest to `/login?username=…`, and offers **Create account** (`/accounts/new`, any signed-in user may add one), **Sign out** of the active account, and **Sign out of all accounts**. A browser stays signed in to up to 8 accounts. The signed-in user can change their password at `/settings/password` (current password required). The change ends every session of the user, so other devices must sign in again; the browser that made the change gets a new session. Sign-up is never open to signed-out visitors, but any account holder can create accounts and see every username — deploy only on a trusted LAN or behind access control.

## Architecture & Data Flow

Single-process Axum 0.8 app (crate `kindle-recipes`, edition 2024, binary-only — no `lib.rs`):

- `src/main.rs` — the hub: `#[tokio::main]` bootstrap, env config, `routes()` router, `AppState`, `AppError`, shared serde types, Askama template structs, form/validation helpers, Codex device-code auth handlers, `run_node_script`.
- `src/auth.rs` — user accounts and cookie sessions: `auth_middleware` (protects every route in the `protected` router and scopes the `ACCOUNT_MENU` task-local that `base.html` reads through `account_menu()`), `AuthUser` extractor, multi-account handlers (`new_account_page` / `create_account`, `switch_account`, `logout_all`), `hash_password` / `verify_password` (Argon2), `setup_page` / `setup_create`, `login_page` / `login`, `logout`, `reset_password_page` / `reset_password`.
- `src/ai.rs` — Pi/Codex generation pipeline: draft create/alter/apply/cancel handlers, `pi_recipe`, `run_pi_worker(_with_credential)`, model catalogue, `recipe_schema` / `validate_generated` / `normalize_generated` / `dedupe_sources`.
- `src/chat.rs` — recipe chat (the **Ask** drawer on the recipe card, which replaced "Alter with AI" and is the only way to change a saved recipe with AI; the old `GET /recipes/{id}/ai/alter` URL is `alter_redirect`, which opens the drawer): `panel` builds the drawer for `recipe_page`, `ask` stores a question with a `pending` answer and runs it on a spawned task (`chat_library` + `library_summary` + `chat_prompt` → `ai::chat_reply` → the worker's `chat` command, whose tools read the recipe's notes, their photos, and saved versions; the system prompt also covers a cook coming back after cooking for pointers next time), `keep_answer` (Keep as note: an answer becomes a whole-recipe note linked by `recipe_notes.chat_message_id`), `toggle_drawer` (open state is the user's `app_settings.recipe_chat_drawer`, so it stays open across edits, views, and recipes), `clear`. When the cook asks for a change, the reply's `change` is drafted through the alter path (`ai::draft_chat_change`, an `alter` draft linked by `ai_drafts.chat_message_id`), and the drawer offers Save change / Preview / Discard. Saving runs `apply_draft`, which calls `recipes::record_chat_change` in its transaction: a `change` row (the zigzag divider, labelled with the model's 1–2 word `label` via `model_label`, else `change_summary` of the diff) marks where the recipe changed, and the version is labelled `Chat: <label>`. `return_target` keeps the drawer's `back` on the same recipe page.
- `src/notes.rs` — the cook's notes: text, a photo, or both, on the recipe as a whole or pointed at one saved version (`recipe_notes.version`, a number rather than a key, so a note still names a deleted version). `panel` builds the block for the recipe page (every note) and each version page (that version's notes; new notes there are about it); `add_note` (multipart, `hx-boost="false"`, photo normalised by `recipes::normalize_upload_jpeg` with `NOTE_PHOTO_FILTER`, at most 1280 px), `update_note` (text and "About"), `delete_note`, `note_photo` (owner only). "About" is `""` (whole recipe), `current` (the newest version, which matches the recipe now; a recipe with no history gets its "Original recipe" version first, `recipes::current_version`), or a version number that must exist. `return_target` keeps `back` on the recipe or one of its version pages.
- `src/recipes.rs` — recipe CRUD handlers **and all SQL accessor helpers** (`find_recipe`, `blocks`, `step_ingredients`, `sources`, `find_draft`, `recipe_snapshot`, …).
- `src/chart.rs` — pure cooking-flow chart builder (`build_chart`, `selected_chart_step`), no I/O.
- `src/thumbs.rs` — local dish-thumbnail pipeline for video imports: ffmpeg frame sampling, pixel scoring, diversity selection, square cropping, and (with the embedding sidecar) `order_by_dish_margin` ranking of a 12-crop pool against dish/non-dish prompts. Pure functions are unit-tested; one integration test needs ffmpeg (present in the Docker builder stage).
- `src/media.rs` — social video import: URL validation, one yt-dlp call for metadata and video (metadata-only fallback), then two lanes on scoped threads — audio ffmpeg → `transcribe_audio`, frames ffmpeg → `read_video_text` — and the OCR planner (`plan_ocr_jobs`: 1 Hz grid of the 4 Hz candidates plus shot-change onsets) and OCR cleaner (`frame_capture` → caption chains → one snippet per card, rows joined with ` / `). `cleaner_prompt` / `recipe_prompt` build the prompts. One blocking job per extraction owns the media permit and a `Workdir` guard; it delivers the evidence as soon as both lanes finish, then runs thumbnails and the moment pool, which `PendingExtras::finish()` collects.
- `src/media_worker.rs` — client for the persistent Python media workers (`pi/local-media.py serve`): one process per kind (transcribe, OCR), started lazily in its own process group, JSON lines on stdin/stdout. A kind serialises its requests; a timeout, a bad or oversized response, or an exit kills the group and drops the worker, and a worker that died after serving is replaced once. Transcription and OCR run concurrently.
- `src/embeddings.rs` — HTTP client for the EmbeddingGemma 2 sidecar (`llama-server --embeddings`, `EMBEDDING_URL`): `Embedder::embed(&[Input::{Text, Image, Audio}])` returns unit 768-d vectors; `blocking()` gives the ffmpeg threads a `BlockingEmbedder`; `document`/`query` add the model's retrieval prefixes; `to_blob`/`from_blob` store vectors as little-endian f32 BLOBs.
- `src/moments.rs` — video step moments: `capture` builds the moment pool during an import (12 s audio windows every 6 s, stills every 2 s, ≤ 40 frame vectors); `match_steps` aligns steps monotonically to audio when the narration clearly talks about the steps (mean lift ≥ 0.06), else to frames; `match_draft` / `refresh_recipe` store the result; `view` builds the page view (time, match source, stills).
- `src/search.rs` — library search over EmbeddingGemma vectors: `recipe_document` builds the text embedded per recipe, `refresh_index` re-embeds recipes whose stored `recipe_embeddings.document` differs from a freshly built one, `search` / `rank` score a `?q=` query (cosine + title bonus, at least 0.60, within 0.10 of the best, max 24), and `backfill` indexes everything at startup (retrying while the sidecar loads). BM25 is the backup: `keyword_terms` / `keyword_rank` score every word of each recipe, read fresh per search with no index (title counted 3×, stopwords dropped, plurals folded, within 25% of the best, max 24). No `EMBEDDING_URL` or a failing sidecar falls back to BM25 silently, never an error. `app_settings.search_engine` (`embeddings`, `bm25`, or `shared`/absent, which follows the first account like AI logins; `keyword_search_selected`, `POST /settings/search-engine`, under Developer tools) makes BM25 run every search. On the home page the search runs as the user types through htmx attributes on the `data-live-search` form (`input changed delay:350ms`, `hx-sync` replace): it fetches `/?q=…`, swaps `#search-results` and (out of band) `#search-title`, and replaces the address bar URL (an empty query becomes `/`). Enter searches at once. Without JavaScript the form submits normally.
- `src/htmx.rs` — htmx glue: the `recipe_flash` one-time notice cookie (`flash_redirect(to, key)` / `flash_cookie(key)` set it, the `Flash` extractor reads it, keys are short lowercase words), `htmx_layer` (outermost layer on every route: clears the flash on the first successful HTML page, sends `HX-Push-Url: false` for a non-GET htmx request answered with a page, and retargets htmx error pages to `.app-shell`), and `full_page_redirect` (`HX-Redirect` for htmx requests, 303 otherwise; the auth middleware uses it for `/login` and `/setup`).
- `src/display.rs` — per-browser display mode: the `recipe_display` cookie holds `colour` or `eink`; no cookie means Automatic, which picks e-ink when the User-Agent contains "Kindle". Every page links `/display.css` after `app.css`; `display_css` (outside auth, `Cache-Control: no-store`) answers an `@import` of `static/eink.css` in e-ink mode and an empty sheet otherwise. `/settings/display` (`display_page` / `update_display`) saves or clears the cookie.

**AppState** is `Arc`-shared into every handler: `db: SqlitePool`, `model`, `pi_worker_path`, `auth_script_path`, `search_grounding: bool`, `codex_flows: Arc<Mutex<HashMap<String, CodexFlow>>>` for in-flight device-code flows, `thumbnail_jobs` and `moment_jobs` (in-flight background runs per recipe id), and `embedder: Option<Embedder>` (`None` turns off search, step moments, and dish-photo ranking).

Front end (load-bearing): every page is still a whole server-rendered document; htmx 1.9 makes it feel like an app. `base.html` loads `/static/htmx.js` and `/static/app.js` (both `defer`, both build outputs) and puts `hx-boost="true"` on `<body>`, so local links and forms fetch the next page with XHR and swap the body in place, push the URL, and update the title. Config lives in the `htmx-config` meta: `historyCacheSize: 0` (no page snapshots in localStorage, since another account may use the browser; Back refetches), `allowEval` and `allowScriptTags` off (no inline scripts anywhere — all behaviour lives in `web/src`). Opt out with `hx-boost="false"` where a whole page must load: the account menu, sign-out, account creation, the display form (its stylesheet is in `<head>`), photo upload and the add-note form (multipart), edit-block links and still links (JavaScript handles those; note photos open in the same still viewer). Status notices never go in the query string: a mutating handler answers `flash_redirect("/page#block", "key")` and the page maps the key to text (Settings shows each notice inside its own block, ids `settings-ai`, `settings-cleaner`, `settings-moments`, `settings-chat`, `settings-account`, `settings-search`; the `#fragment` only matters without JavaScript). Settings forms swap just `#settings` (`hx-select`/`hx-target`, `show:none` keeps the scroll); recipe block forms swap the body with `show:none`; chart links swap `.paper` with `hx-replace-url`. Background work is polled with hidden `hx-trigger="every 3s"` pollers (`hx-indicator="this"`): `data-poll-unless-editing` skips a tick while an edit (or a note's Edit form) is open, and `data-swap-when-gone="<selector>"` holds the swap until the marker is gone from the response (the chat drawer's poller names its current `data-chat-state` token, so it swaps once an answer or draft moves on). The chat drawer's question form, Clear, and poller swap only `#recipe-chat`; Save change and Discard reload the body. Errors (4xx/5xx) are swapped into `.app-shell`. Codex and Claude sign-in opens in a popup on Settings (`auth-popup.ts`): Reconnect / Connect `hx-get` the sign-in page's `#auth-flow` into `#auth-popup-body` (the provider form sets `hx-disinherit` so its links do not take its `#settings` swap), the flow's forms and links swap `#auth-flow` (so the page also works on its own), and a finished step answers `htmx::finish_popup` (204 + flash + `HX-Trigger: popup-finished`), which closes the popup and refreshes `#settings`. When htmx fails to load, `app.js` wires the page once and everything works as plain HTML.

Data flow: HTTP request → handler (extractors `State<Arc<AppState>>`, `Path`, `Form`, `Query`) → sqlx helpers or the AI pipeline → Askama template struct → HTML. Every page is a server-rendered template in `templates/`; forms post `application/x-www-form-urlencoded` via axum `Form`.

Accounts (load-bearing): the browser holds the active session's token in `recipe_session` and the tokens of its other signed-in accounts in `recipe_accounts` (joined with `.`, same cookie attributes and lifetime). `browser_sessions` resolves both to live sessions, active first, one per user. The middleware drops ended tokens from `recipe_accounts`, and when the active session has ended it promotes the first remembered one. Signing in (`login`, `create_account` → `sign_in_browser`) makes the new session active and keeps the others behind it (an older session of the same user on this browser ends). `POST /accounts/switch` swaps the active token with a remembered one and opens `/`; an account this browser is not signed in to goes to the sign-in page. `POST /logout` ends only the active session and hands the browser to the next remembered account (else `/login`); `POST /logout/all` ends every session the browser holds. The account menu reaches templates through the `ACCOUNT_MENU` task-local, not template fields: pages outside the middleware (`login.html`, `setup.html`, or anything rendered on a spawned task) get no menu. AI logins are shared by default: `ai_account(db, user_id)` resolves the account whose provider, subscriptions, endpoints, models, effort, and video cleaner serve a user's generations, which is the first account (`shared_ai_account`) unless the user saved `app_settings.ai_logins = "own"` (`POST /settings/ai-logins`, mode `own` or `shared`; their own setup is kept either way). Generation entry points (`ensure_ai_configured`, `pi_recipe`, `ensure_media_cleaner_configured`, `clean_media_evidence`) resolve it first, so a shared subscription's refreshed token is stored back on the owning account. Settings shows a sharing account only a summary of the shared setup (never its keys) and a switch; the edit handlers always act on the signed-in user's own setup. `app_settings` is keyed by `(user_id, key)`, so every settings accessor (`ai_provider`, `selected_model`, `selected_effort`, `step_moments_enabled`, `media_cleaner_setting`, …) takes the user id; `reconcile_ai_provider` heals each user's value against that user's own endpoints.

Auth flow (load-bearing): every library route sits behind `auth_middleware` (`from_fn_with_state` on the `protected` router; `/setup`, `/login`, `/logout`, `/logout/all`, and `/healthz` are outside it). A valid `recipe_session` cookie → the user id is inserted into request extensions as `AuthUser`, which handlers take as an extractor. No valid session and no `users` row → redirect to `/setup`; no valid session otherwise → 303 to `/login` (a GET carries its path and query in `?next=`, other methods go to `/login` plain). `POST /login` checks the password against `users.password_hash` with Argon2 (an unknown username costs the same dummy check), then creates a session and redirects to `next` only when it is a local path (`local_target` refuses `//host`, `/\host`, and absolute URLs). Sessions live in the `sessions` table: the cookie holds 32 random bytes (base64url), and the table holds only their SHA-256 (`token_hash`). A session ends 30 days after its last use. The middleware extends it at most once a day and then sends the cookie again with `Max-Age` of 30 days. The cookie is `Path=/; HttpOnly; SameSite=Lax` and has no `Secure` flag, because the app serves plain HTTP on the LAN. `POST /logout` deletes the session row and clears the cookie. `POST /settings/password` re-verifies the current password, then replaces the hash, deletes all of the user's sessions, and issues a new one in one transaction (the single password page is "Reset password" at `/settings/password`, linked from the Account block in Settings). Setup signs the new account in the same way. The `users` table is the single source of truth — never a config file.

AI flow (load-bearing): `POST /ai/generate` with a single Facebook/Instagram video link in the prompt (`social_video_in_prompt`) hands off to `import_recipe` with every source on and the rest of the text as notes; otherwise `POST /ai/generate` → `create_draft` → `spawn_blocking` runs `node pi/recipe-worker.ts` (one JSON request on stdin, one JSON line on stdout) with a **per-request `0o600` temp `auth.json`** materialized from the DB credential; the worker's token refresh is read back and persisted via `store_codex_credential`; result lands in `ai_drafts` with `expires_at = now + 24h`; the preview page shows it and `apply_draft` persists in one transaction under a `base_updated_at` staleness guard (rejects if the recipe changed meanwhile). The active provider is `app_settings.ai_provider`: `"pi"` (Codex) or an `ai_endpoints` row id; `pi_recipe` dispatches Codex to the Pi SDK path and endpoint ids to `endpoint_recipe`, which sends the spec, base URL, key, and model to the worker — the key never round-trips back. Specs: `openai` (Responses API) and `anthropic` (Messages API) run the worker's own code with native web search; every other spec is a pi-ai built-in provider id (`google`, `mistral`, `xai`, `deepseek`, `openrouter`, `groq`, `together`, `fireworks`, `cerebras`, using pi-ai's catalogue and base URL, so `base_url` is stored empty) or `openai-compatible` (a custom Chat Completions server, key optional). pi-ai endpoints have no web search: `endpoint_search_mode` turns a grounded request into `off`. Settings adds a provider from `PROVIDER_PRESETS` (pick a provider, paste a key; only "Other server" asks for a URL and model) and makes it active. The video cleaner (`cleanMedia`) runs through the same backends (`resolve_backend`): `app_settings.media_cleaner_provider` (empty follows `ai_provider`) and `media_cleaner_model` (empty uses the provider's model); `0016_media_cleaner_provider.sql` turned the old Vercel AI Gateway credential into an `openai-compatible` endpoint.

Key invariants:

- AI output must pass `validate_generated` (every ingredient used exactly once, `inputSteps` only reference earlier steps, …) before any draft is saved.
- `recipes.chart_json` is AI-derived only; any manual block edit MUST call `invalidate_chart` so the viewer falls back to linear inference.
- Dish thumbnails come only from two local paths — the ffmpeg scoring pipeline during an import, or a user-uploaded image normalised through ffmpeg on the recipe card — never a cloud service. Draft candidates live in `draft_thumbnails` and recipe re-pick candidates in `recipe_thumbnail_candidates`; both MUST die when consumed (apply/choose/remove/discard/expiry). Only chosen JPEGs are copied into `recipes.thumbnail_jpeg`. Thumbnail bytes are served exclusively to the owning user and never logged. In-flight re-pick runs are tracked only by the in-memory `AppState.thumbnail_jobs` set, so a restart drops "pending" back to idle.
- The Codex credential is DB-only; Pi SDK invocations MUST use `run_pi_worker_with_credential`, never a fixed-path credential file.
- Endpoint API keys live in the `ai_endpoints` table, never in env or config; templates only ever receive the masked tail (`mask_key`), and the add/switch/delete handlers (`add_endpoint` / `update_settings` / `delete_endpoint`) are the only mutators. Deleting the active endpoint falls `ai_provider` back to `"pi"`; `reconcile_ai_provider` heals stale values at startup.
- Refused logins: the worker reports an OAuth refresh the provider rejected, a 401, or an invalid key as `code: "auth"` (`isAuthFailure` / `workerFailure` in `pi/recipe-worker.ts`). `ai::track_login` (wrapped around every subscription and endpoint worker run) stamps `pi_credentials.auth_failed_at` / `ai_endpoints.auth_failed_at` and returns `AppError::AiLoginRefused` (never retried; the error page and the import page link to Settings); a run that signed in, a stored token refresh, or a reconnect clears it. A subscription `listModels` does not prove the login, so it never clears the flag. Settings shows "Sign-in expired" / "Key rejected" on the row and offers **Refresh sign-in** (`POST /settings/check/{codex|claude}`, the worker's `checkLogin` → `CheckLoginResponse`, which forces an OAuth refresh) and **Test key** (`POST /settings/endpoints/{id}/check`, a model listing); both flash `*_login_works` / `endpoint_key_works`, `login_refused`, or `login_check_failed` into the AI block.
- LLM call logging: every generation logs the full request (provider, model, attempt, prompt, system prompt) and the full response (recipe + sources JSON, elapsed ms) at `info` level, and the worker's stderr is forwarded into the app log, so `docker compose logs` shows the whole call. Only selected fields are logged — `apiKey`/`authPath` never appear.
- Notes: every `recipe_notes` query is scoped by `user_id` and `recipe_id`; note photos are local like dish photos (ffmpeg-normalised uploads only), served only to the owner, and never logged. The chat sends notes to the worker in the request's `library` (the newest 40 notes, the newest 6 photos as base64, the newest 12 versions plus any a note names); the host log shows the notes' text and `photoSent` flags through `ai::chat_library_log`, never photo bytes, and the worker logs each tool call by name and arguments.
- Recipe chat: every `recipe_chat_messages` query is scoped by `user_id` and `recipe_id`, so a thread is only ever read, answered, or cleared by the account that wrote it (another account gets 404). The chat never writes a recipe: a requested change becomes an ordinary draft, saved through `apply_draft` (validation, staleness guard, version history, moments). Answers and drafts left `pending`/`drafting` by a restart are failed at startup (`fail_interrupted_chats`). The user's `app_settings.recipe_chat` switch (`chat_enabled`, default on; `POST /settings/recipe-chat`) hides the drawer and 404s its routes. In SQL, never mix `?` and `?N` placeholders in one query: sqlx binds the unnamed ones out of order.
- Passwords are stored only as Argon2 hashes (`users.password_hash`); `reset_password` MUST verify the current password first and never log or return password material. Session tokens are never stored or logged: `sessions` keeps only `token_hash`.
- The embedding sidecar is the only place images, audio windows, and text are embedded; it runs on the same host (compose service `embeddings`), so frames never leave the machine. Every embedding feature degrades when it is absent: search falls back to BM25, imports skip the moment pool, and dish photos keep the heuristic order.
- The video moment pool (`draft_moment_vectors`, `draft_moment_stills`) rides with the draft (FK cascade on `ai_drafts`), is copied along alteration chains, and `apply_draft_moments` moves it to `recipe_moment_vectors` / `recipe_moment_stills` inside the apply transaction before the draft row is deleted. A recipe saved without a pool gets one from `POST /recipes/{id}/moments/capture` (`start_moment_capture`): a background run downloads the social video again (`extract_fresh_moment_pool`), `store_recipe_moment_pool` replaces the pool, and `refresh_recipe` matches the steps; `AppState.moment_jobs` tracks the run in memory only. `recipe_step_moments` is keyed by step block id (moves keep it, deletes cascade); every block mutation calls `moments::spawn_recipe_refresh`. Stills are served only to the owning user. The user's `app_settings.step_moments` switch (`step_moments_enabled`, default on) gates capture and display for that user's recipes and drafts.
- Media extraction: transcription and OCR evidence is delivered before thumbnails and the moment pool, so the cleaner and draft calls run while those finish; the extraction job always removes its work directory before it releases the media permit, and dropping `PendingExtras` cancels the moment stage. OCR cleaning has no word or all-caps allowlists: precision comes from row confidence plus corroboration across frames (a row needs two samples; a one-sample card needs standalone strength). Never feed the caption to Whisper as `initial_prompt` or `hotwords` (measured: the transcript collapses). Page titles that embed the caption are reduced to the account (`account_title`); `MediaEvidence.audio_segments` is `#[serde(default)]` so stored evidence stays readable.

## Development Commands

All development, benchmarking, experimentation, dependency/package installation, builds, and testing MUST run inside Docker. Do not run Rust, Node, Cargo, npm, benchmark, or packaging/install commands directly on the host machine. Use the project Docker/Compose environment (or an equivalent disposable development container) so the local machine is not modified by toolchains, caches, dependencies, or generated artifacts.

```sh
docker compose up --build         # full stack (what deploy.sh runs on the target host; only through deploy.sh): app on port 3000 plus the `embeddings` sidecar (llama.cpp, EmbeddingGemma 2 Q8_0; first start downloads ~870 MB into the embedding-models volume)
./deploy-local.sh                 # local Docker deploy; do not use on this machine (see below)
docker compose run --rm <service> <command>  # run build, test, fmt, clippy, benchmarks, or installs in a container
./deploy.sh [ssh-target] [--no-backup]  # build, back up the live SQLite DB to ~/recipe-backups, docker compose up -d, wait for /healthz (default target minibuntu; a target naming this host deploys locally, any other goes over DOCKER_HOST=ssh://)
```

Do not start the app stack by hand: no bare `docker compose up` or `./deploy-local.sh`. To run or check the app, deploy it to minibuntu with `./deploy.sh minibuntu` and check `http://minibuntu:3000/healthz`; on minibuntu itself that deploys to the local daemon. `deploy.sh` is gitignored (host-specific), so a fresh checkout has none. Local one-off containers for builds and tests (`docker compose run --rm …` or `docker run --rm …`) are still allowed.

The binary accepts `--healthcheck` (probes `GET /healthz` without starting the server; used by the compose healthcheck).

## Code Conventions & Common Patterns

- **Handlers**: `pub(crate) async fn` free functions, `State<Arc<AppState>>` first, returning the crate alias `type Result<T> = std::result::Result<T, AppError>`. Page-render handlers are named `*_page`; mutators follow `update_/delete_/add_/move_/alter_/apply_/cancel_*`.
- **Errors**: one `AppError` enum (thiserror) in `main.rs` with a single `IntoResponse` mapping — `NotFound`→404, `BadRequest`→400, everything else→500. Extend `AppError`, never introduce per-module error types. Log once at the boundary: `error!(error = %self, "request failed")`.
- **SQL**: sqlx 0.8 raw queries (no `query!` macros), row types via `#[derive(FromRow)]`, multi-step writes inside `sqlx::Transaction` passed as `&mut sqlx::Transaction<'_, sqlx::Sqlite>`. All DB accessors live in `src/recipes.rs`.
- **IDs & timestamps**: `Uuid::new_v4().to_string()` TEXT PKs; timestamps are RFC3339 strings via `stamp()`. Do not introduce INTEGER ids or epoch timestamps.
- **Config**: `dotenvy::dotenv().ok()` with defaults read in `main()`; boolean switches via `env_bool(name, default)`; user-visible settings persist in the `app_settings` key/value table, not env.
- **Async**: `#[tokio::main]`; blocking Node subprocess work inside `tokio::task::spawn_blocking` with plain `std::process::Command`.
- **Logging**: `tracing` + env-filter; `info!`/`warn!`/`error!`; HTTP via `TraceLayer`.
- **Templates**: Askama structs with `#[template(path = "...")]`; new pages extend `templates/base.html`; `{% match %}` for Rust Option/enum rendering.
- **Shared types** (serde, camelCase renames for AI wire types) live in `main.rs` — keep them there, not in feature modules.
- Form validation helpers in `main.rs`: `required(s, name)`, `trim`, `number(s)`.

## Important Files

- `src/main.rs` — entry point; `routes()` (router table at `main.rs:396`), `AppState`, `AppError`, `anyhowless` module (startup error alias deliberately avoiding an anyhow dep).
- `src/auth.rs` — setup, sign-in, and sign-out pages, cookie-session middleware, Argon2 hashing, password change handlers.
- `Cargo.toml` / `Dockerfile` / `compose.yaml` / `deploy.sh` / `.env.example` — build, deploy, env contract.
- `pi/recipe-worker.ts` — the worker protocol contract (typed as `WorkerRequest`, `GenerateResponse`, `ListModelsResponse`, `CleanMediaResponse`, `WorkerFailure`): stdin JSON `{prompt, systemPrompt, model, reasoningEffort, searchMode, authPath}` with `provider: "openai"` (adds `apiBaseUrl`/`apiKey`, Responses API) or `"anthropic"` (Messages API, `web_search_20250305` tool, prompt-cache breakpoint on the system prompt, `pause_turn` continued up to 5 times), or `{command: "chat"}` (same fields plus `library` `{notes, versions, currentVersion}`; answers one recipe-chat turn without web search. Every backend, the native OpenAI/Anthropic specs included, runs through pi-ai here (`chatModelCall`) so the model can call `CHAT_TOOLS`, `recipe_notes` / `note_photo` / `recipe_version`, which `runChatTool` answers from the library inside the worker; `chatWithTools` allows `CHAT_TOOL_ROUNDS` (4) turns of lookups, a photo goes only to a model whose `input` includes images, and the reply prints `ChatResponse` `{reply, change, label, toolCalls}`; `chatReply` takes prose that ignored the JSON format as a plain answer), or `{command: "listModels"}` (a subscription's pi catalogue; with `provider`/`apiBaseUrl`/`apiKey` the endpoint's own `/models` list, Anthropic pages followed). Every listing is cached per source (pi provider id or endpoint id) for 15 minutes by `discover_models`, and Settings offers it for Codex, Claude, and each endpoint. `searchMode` is `off|grounded|gapfill` — `grounded` must research and cite, `gapfill` attaches `web_search` without requiring it (From Video imports fill gaps in untrusted evidence; sources stay optional because the social post is appended as attribution). stdout `{recipe, sources}` or `{error, code}` (`code: "configuration"` → `AiNotConfigured`). `reasoningEffort` is `low|medium|high|xhigh|max`, default `low`. Anthropic endpoints on Claude 4.6 and later (or an unrecognised model id) get adaptive thinking with `output_config.effort` (`xhigh` runs as `max` on the 4.6 models); earlier models get `budget_tokens` per effort, with `xhigh`/`max` capped at the highest budget. The worker logs each Messages API call's cache usage (`anthropicUsage`) to stderr.
- `migrations/0001_initial.sql` — core schema (`recipes`, `recipe_blocks`, `recipe_sources`, `ai_drafts`); later migrations add `recipe_step_ingredients`, `recipes.chart_json`, `pi_credentials`, `app_settings`, `0006_users.sql` adds the `users` table for the account, `0008_ai_endpoints.sql` adds the `ai_endpoints` registry (OpenAI/Anthropic-spec endpoints with keys), `0011_recipe_thumbnails.sql` adds `recipes.thumbnail_jpeg` plus the expiring `draft_thumbnails` candidates, `0014_embeddings.sql` adds `recipe_embeddings` (search index) and the draft/recipe moment pools plus `draft_step_moments` / `recipe_step_moments`, `0015_sessions.sql` adds the `sessions` table (hashed sign-in tokens, cascade-deleted with the user), `0017_user_settings.sql` keys `app_settings` by `(user_id, key)`, handing existing values to the oldest account, and `0019_recipe_chat.sql` adds `recipe_chat_messages` (one private thread per user and recipe: questions, answers, and `change` dividers, read in rowid order) and `ai_drafts.chat_message_id`, and `0020_recipe_notes.sql` adds `recipe_notes` (text and/or a photo JPEG, an optional version number, and the chat answer a note was kept from).
- `templates/recipe_chat.html` — the chat drawer, included by `recipe.html` below the card actions in both views when the drawer is open.
- `templates/recipe_notes.html` — the notes block, included by `recipe.html` (card view, after the method) and `version.html`; reads a `notes` (`NotesPanel`) field.
- `templates/step_moment.html` — the shared step moment block (time, match source, and stills; each still is a `data-still-viewer` link (`hx-boost="false"`) that `app.js` opens in a full-page viewer), included by `recipe.html` (card and chart detail) and `draft.html`.
- `templates/recipe.html` — largest template: inline edit forms, block move/delete, chart view. The recipe, draft, and version pages share the index-card markup: a `.recipe-sheet` with `.page-header`, `.card-rule`, `.recipe-facts`, `.card-actions`, and a `.card-body` of `.ingredient-row`s and `.step-group`s. The library (`home.html`) files recipes A to Z (`file_by_letter`) as order tickets: the first row hangs from a single ticket rail, and `app.css` pins every later row to the wall with a CSS pushpin (which tickets make up the first row depends on the column count). Each ticket prints the recipe's ingredients (`attach_ingredients`, one query), in two columns past `TICKET_COLUMNS_AFTER`. `templates/setup.html`, `templates/login.html`, `templates/account_new.html`, and `templates/password_reset.html` are the auth screens; the account menu lives in `templates/base.html`.

## Runtime/Tooling Preferences

- **Rust**: edition 2024 (needs ≥ 1.85; Docker pins `rust:1.88-slim`). glibc, not musl. `sqlx` 0.8 no-default-features (tokio-rustls, sqlite, migrate); `reqwest` with rustls (no native-tls).
- **Node**: ≥ 22.23.4 (`node:22.23.4-bookworm-slim`, pinned in every Dockerfile stage: the first 22.x with the bundled Brotli decoder fixed, CVE-2026-111497), ESM (`"type": "module"`), npm. The `pi/*.ts` files ship and run as-is through Node's built-in type stripping (unflagged since 22.18, no warning), so they use erasable syntax only: no enums, namespaces, parameter properties, or `import =`; `import type` for type-only imports; relative imports end in `.ts`. `pi/tsconfig.json` only type-checks (`noEmit`, `strict`, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `nodenext`); dev dependencies `typescript` (5.9.x; 5.x because the browser code compiles to ES5) and `@types/node` (22.x) are pinned and never needed at runtime (`npm ci --omit=dev`); `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent` pinned together at `1.3.0` — keep them in lockstep. Subscription providers run through `ModelRuntime`: `openai-codex` (Codex) and `anthropic` (Claude Pro/Max OAuth); the worker request field `piProvider` selects one. pi-ai applies Anthropic prompt caching for the Claude subscription itself (5-minute TTL by default; `PI_CACHE_RETENTION=long` selects 1 hour).
- **Env vars** (`.env.example`): `DATABASE_URL` (`sqlite:/data/recipes.sqlite3`), `APP_BIND` (`0.0.0.0:3000`), `PI_MODEL` (`gpt-6-luna`), `PI_SEARCH_ENABLED` (default `true`), `THUMBNAILS_ENABLED` (default `true`; disables dish-photo candidate extraction when false), `EMBEDDING_URL` (compose sets `http://embeddings:8080`; empty turns off search, step moments, and dish-photo ranking), `RUST_LOG` (`kindle_recipes=info,tower_http=info`), optional `PI_WORKER_PATH` / `PI_AUTH_SCRIPT_PATH` / `PI_CLAUDE_AUTH_SCRIPT_PATH` / `PI_CODING_AGENT_DIR`. Media knobs (all optional, documented in `.env.example`): `MEDIA_OCR_BASE_HZ` (1), `MEDIA_OCR_CUT_RATIO` (2), `MEDIA_OCR_TEXT_GATE` (`true`), `MEDIA_OCR_GATE_SIDE` (640), `MEDIA_WHISPER_MODEL` (`base`), `MEDIA_WHISPER_BATCH_SIZE` (8), `MEDIA_WORKER_IDLE_SECONDS` (600). No OAuth tokens in `.env` — the Codex and Claude credentials live in the DB.
- Migrations run via compile-time embedded `sqlx::migrate!()`; any schema change is a new numbered `migrations/000N_*.sql`.
- **Browser code**: TypeScript in `web/src`, compiled to ES5 because older Kindle browsers parse nothing newer. Only the ES5 library is visible to the type checker, so `Promise`, `Array.from`, `String#includes` and the like fail the build; the DOM lib still declares `NodeList.forEach`, `Element.closest` and `matches` without the webkit fallback, so use the `dom.ts` helpers instead. A feature registers with `onPage(root => …)` and must find its elements inside `root` (it runs on the first page and on every swapped-in fragment; `firstTime` guards double setup); long-running loops stop once their element is no longer attached. Delegated `document` listeners are registered once. htmx is pinned at `htmx.org` 1.9.12 (dev dependency; 2.x drops the older browsers).
- `.agents/` skills are coding-agent tooling, excluded from the Docker image.
